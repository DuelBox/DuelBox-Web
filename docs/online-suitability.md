# Online-multiplayer suitability, per game

Turn-based board games work over any latency; real-time physics duels need the fixed
timestep run in lockstep, and not all of them are worth porting. This is the classification
issue #237 asks for: **every game placed in a class, with the reason it is there**, derived
from the two manifest fields that actually decide it rather than from a per-game opinion.

Read `docs/play-configurations.md` first — it establishes that Remote is one of the three
configurations every game already declares support for, and that the simulation runs on the
player's device in all three. Online multiplayer is not a new product; it is Remote with the
*other* player's inputs arriving over a wire instead of from the seat beside you. And read
`docs/input-parity.md` for why one archetype cannot be paired across input families at all.

## How a game is classified

Two manifest facts, and nothing else, so the table cannot drift from the catalogue:

- **`archetype`** — how the two seats interact *in time*.
  - `turn-board`, `turn-aim`: **one seat acts at a time.** The other is waiting by the rules
    of the game, so any latency is absorbed by the turn. These need no lockstep — an
    authoritative exchange of moves is enough, the way correspondence chess is enough.
  - `rt-split`, `rt-arena`, `rt-race`: **both seats act at once.** Two devices stepping the
    same match must agree on every frame, which is exactly what the fixed timestep and seeded
    RNG (CLAUDE.md rules 4, 5, 8) were built to allow — but only once inputs are exchanged in
    lockstep with a delay and the state is hashed to catch desync (issue #240).
- **`sameInputClassOnly`** — whether the game can be made fair across input families. When
  set, an online match must pair two devices of the *same* class (both keyboards, or both
  touchscreens); one of each is a match one player cannot win, so the pairing is refused
  rather than shipped. See `docs/input-parity.md`.

The table below is generated by `scripts/emit-online-suitability.mjs`, which reads `archetype`
from `data/catalog.generated.json` and `sameInputClassOnly` from each
`packages/games/<id>/src/manifest.ts`. Re-run it and paste its output between the markers when
the catalogue changes; the doc is the artefact, so nothing is written automatically.

## The three classes, and the work each implies

| Class | Games | What it needs | Rough work |
|---|---|---|---|
| **Latency-tolerant** (turn-based) | 46 | Authoritative move exchange over the room server (#238); a turn timer that Together does not need, because there is no social pressure across a wire (`docs/play-configurations.md`); reconnect grace (#242). No lockstep. | Lowest. The move is the whole payload, and a late move is a slow game, not a broken one. |
| **Lockstep** (real-time, any pairing) | 54 | Deterministic lockstep with input delay and desync detection (#240) over WebRTC data channels with a TURN fallback (#239); reconnect grace (#242). | Highest. This is the netcode the fixed timestep was built to make possible, and it is one engine-level feature all 54 then inherit. |
| **Lockstep, same input class only** | 8 | Everything the row above needs, **plus** a matchmaking constraint: the room may only pair two devices in the same input family, because `rt-race` is rapid discrete input a thumb cannot match a key at. | Highest, plus a pairing rule the lobby must enforce and explain. |

Every game lands in exactly one of the three. Nothing is `local-only`: the simulation is
device-side in every configuration, so any game *can* be played remotely once its class's
netcode exists — the classes are about *how much* netcode and *which pairings*, not about
whether it is possible at all. A game that genuinely cannot be networked would have to be one
the engine cannot make deterministic, and CLAUDE.md rule 8 forbids shipping one of those.

## The recommended launch subset

Ship the **46 latency-tolerant games first.** They are the cheapest netcode (move exchange,
no lockstep), they are the games where a slow connection degrades gracefully rather than
desyncing, and Chess-and-friends over a link is the most recognisable "play a friend online"
promise. The room server (#238) plus invite links (#241) plus reconnect grace (#242) is the
whole dependency list, and none of it needs WebRTC.

Then the **54 any-pairing lockstep games**, gated on #239 (data channels + TURN) and #240
(lockstep). This is one engine feature that unlocks all 54 at once, which is the argument for
doing it rather than porting games one at a time.

The **8 same-input-class games** ship in that second wave but with a matchmaking rule and a
line of copy: an online match is offered only between two devices of the same input family.
They are the smallest group and the one with a caveat a player has to be told about, so they
are the last to turn on and the first to need product sign-off.

## A discrepancy this classification surfaced

`docs/input-parity.md` rules that **every `rt-race` game** is same-input-class only — the
interaction *is* rapid discrete input, which no normalisation fixes. There are eight `rt-race`
games in the catalogue, but only **`road-dodge` declares `sameInputClassOnly: true`** in its
manifest. The other seven — `crash-it`, `racing-cars`, `rat-race`, `slot-cars`, `taxi-race`,
`traffic-jam`, `wheelie` — inherit the schema default of `false`.

The table below classifies all eight as same-input-class **by archetype**, because that is
what the input-parity ruling requires. But the manifests and the doc disagree, and the
manifest is what a matchmaking system would actually read. This is a manifest fix (add
`sameInputClassOnly: true` to the seven `rt-race` manifests, each with the reasoning
`road-dodge`'s carries) and it is outside the scope of this document — filed as an observation
for the owner rather than fixed here, because a game manifest is the game's to change.

## Acceptance criteria status

- **Every game classified with a reason.** Done — 108 games, the reason for each being its
  archetype (the time-interaction it implies) and its `sameInputClassOnly` flag, both read
  from the manifest by `scripts/emit-online-suitability.mjs` rather than assigned by hand.
- **Work estimated per class.** Done — the table above, in dependency terms (#238 / #239 /
  #240 / #241 / #242) rather than in hours, because the estimate that matters is *which
  netcode feature* each class waits on.
- **Launch subset decided.** Recommended above (the 46 latency-tolerant games first). It is a
  recommendation for the owner to ratify, not a build decision this document can make alone —
  none of the netcode it depends on exists yet, and `docs/play-configurations.md` records that
  Remote is the one configuration that is not offline-capable.
